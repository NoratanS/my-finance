1 · Give the active profile one home

backend/…/security/ActiveProfile.java (53)
backend/…/service/TransactionService.java (268) · CategoryService.java (200) · BudgetService.java (168) · SubscriptionService.java (240) · InsightService.java (113)
backend/…/service/AuthService.java (132, self-heal at 118–124)
Problem
ActiveProfile is shallow: it hands out a raw id, and five classes each finish the scoping ritual themselves.
Solution
Deepen ActiveProfile so it resolves the request's Profile, verifies it still exists, supplies the reference for inserts, and answers the 404 for rows that belong elsewhere.

Wins

  • locality: deleted-profile rule lives once
  • leverage: one interface, 33 call sites
  • scoping tested at one interface
  • four copies of requireCategory deleted

Evidence

  • 33 × activeProfile.requireId() across 5 classes (10 · 5 · 6 · 6 · 6)
  • requireCategory is identical in 4 classes — TransactionService:263, SubscriptionService:232, BudgetService:163, CategoryService:178
  • getReferenceById(profileId) in 4 classes — TransactionService:76, SubscriptionService:84, BudgetService:66, InsightService:53
  • The deleted-profile defect was fixed twice, caller by caller: AuthService, then CategoryService — commit 472574e: "this caller was missed"
  • The other four have no handling and no test. The maintenance ledger flagged them as answering 409 instead of 404; by my reading Insight writes hit the foreign key (409), while Transaction, Budget and Subscription writes fail earlier on the cascade-deleted Category — a 404 that blames the wrong thing. Neither was reproduced
  • ArchitectureTest.java:14 — profile scoping "remains a human review concern"

Tests
Per-endpoint isolation tests stay — they cross the HTTP interface. Wrong-profile and deleted-profile rules gain one test surface instead of one per class.

Against
Verifying the Profile costs one SELECT per write — the ledger's stated reason for leaving it.

No conflict with ARCHITECTURE.md §3: scoping stays server-side, in the service package, with no persistence-level filter tricks.

4 · One home per value rule

backend/…/dto/TransactionRequest.java · SubscriptionRequest.java · UpdateSubscriptionRequest.java · CreateBudgetRequest.java · UpdateBudgetRequest.java
backend/…/dto/CreateProfileRequest.java · CreateCategoryRequest.java · UpdateCategoryRequest.java
backend/…/service/BackupValidator.java (283)
Problem
What counts as a valid amount, currency, colour or name is restated in every request record and hand-copied into the backup validator.
Solution
Each value rule becomes one module — a composed Bean Validation constraint is the conventional Spring shape — used by the request records and by backup restore.

Wins

  • locality: one rule, one test
  • leverage: Phase 6 adds money fields
  • backup and endpoints cannot disagree
  • two identical records become one

Evidence

  • The money rule (4 stacked annotations) sits on 5 request records; BackupValidator.java:227–242 is a hand copy that says so: "Same rules as @DecimalMin + @Digits"
  • Currency pattern on 6 records + BackupValidator.java:31; colour pattern in 3 places; the length limit of 100 at 11 sites
  • CreateBudgetRequest and UpdateBudgetRequest differ in their name and one comment line
  • The rule is tested for Transaction and Budget; SubscriptionControllerTest has no such test
  • Cross-field checks surface as pseudo-fields (occurredOnNotInFuture, passwordWithinBcryptLimit, periodValid); the frontend renames the first two by hand — see card 2

Tests
One table-driven test per rule. Per-endpoint tests keep a single "invalid body is 400"; BackupValidatorTest keeps its file-integrity cases.

Against
These rules rarely change, and stacked annotations are idiomatic and readable where they stand. The payoff arrives with the next money-bearing record.

5 · One form idiom, one money input

Wins

Tests

Against
The current tests are fast, readable and already written, and 17 e2e tests cover integration. A rewrite is not justified. If this is not wanted, remove msw.

13 · Sessions move into the Postgres already there

backend/pom.xml (40–43 session starter, 102–106 testcontainers-redis) · src/main/resources/application.properties (51–57)
docker-compose.yml (23–32, 41, 54–55, 122) · deploy/release/docker-compose.yml
backend/src/test/…/support/TestcontainersConfiguration.java (38) · config/SessionSurvivesRestartTest.java (163)
Problem
A Redis container, its volume and its healthcheck exist to hold one user's HTTP session.
Solution
Spring Session's JDBC store keeps sessions in the Postgres the stack already runs; Flyway adds its two tables.

Wins

  • one container, one volume fewer
  • two Maven dependencies removed
  • restart survival kept
  • test suite starts one container

Evidence

  • A search of src/main for Redis finds two comments and no code: it only backs the session store
  • SessionSurvivesRestartTest starts two Spring contexts against one store — it restarts the backend, not Redis — so it keeps proving the same thing against Postgres
  • ARCHITECTURE.md gives two reasons for Redis. Restart survival needs a durable store, which Postgres is. A second backend instance is ruled out by the same document's §7 non-goals
  • Goes away: the redis block in both compose files, redis-data, two depends_on entries, REDIS_HOST/REDIS_PORT, the session-data-redis starter, testcontainers-redis, one Testcontainers bean

Tests
Every @IntegrationTest already runs the real session filter; they keep doing so with one container fewer. The pinned serialVersionUID stays relevant — the JDBC store serialises the same way.

Against
Each authenticated request updates a session row in Postgres. Negligible for one user. Existing sessions are lost once, at the upgrade.

Contradicts ARCHITECTURE.md §3 — "Sessions are stored in Redis". Worth reopening: the requirement is a store that outlives the backend, not Redis specifically. It is the reasoning that removed Prometheus and Grafana on 2026-09-22, applied once more.

backend/…/service/TransactionService.java (constructor) · backend/src/test/…/mapper/TransactionMapperTest.java (73)
Problem

Wins

  • one mapping idiom, not two
  • a missing field fails the build

Contradicts ARCHITECTURE.md §3 — "Why MapStruct, and why only in one place". Worth reopening: the build-error guarantee it cites is what a record's constructor already gives, and MapStruct as configured does not give it.

15 · Make the OpenAPI schema earn its keep

backend/pom.xml (52–56) · backend/…/config/OpenApiConfig.java · 18 records carrying 33 × @Schema
frontend/src/api/schema.d.ts (1,966, generated) · src/api/types.ts (371) · src/api/hooks/* (688) · package.json (generate:types)
.github/workflows/ci.yml (75)
Problem
The schema is paid for in full — Jackson 2 on the classpath, 33 hand-placed annotations — but the frontend derives 12 types from it, the generated file is stale, and nothing in CI notices.
Solution
Make the OpenAPI document the one statement of the wire contract: checked for drift in CI, and accurate enough that response types derive from it too.

Wins

  • drift becomes a CI failure
  • types.ts shrinks toward aliases
  • locality: money schema stated once
  • wire contract has one source

Evidence

  • schema.d.ts is imported by one file. 12 of 57 types derive from it; paths and operations are used 0 times, so URL, method and response type are paired by hand at 42 call sites
  • The generated file predates passwordless mode: no authMode on the session, no /api/auth/password — both already used by the frontend
  • ci.yml:31 lints, tests and builds; nothing regenerates or compares the schema. generate:types needs a backend running on localhost:8080
  • Response types are hand-written for a recorded reason: springdoc emits every response field as optional (commit feabb01)
  • @Schema(type = "string", format = "decimal") appears 22 times. springdoc can replace a type's schema globally (SpringDocUtils.replaceWithSchema) — the same move JacksonConfig makes for the wire format
  • Jackson 2 databind reaches the classpath only through springdoc (mvn dependency:tree -Dverbose); that cost stays while springdoc needs it

Tests
One backend test pins the served document; one CI step regenerates the types and fails on a diff. HttpMessageConverterTest and the ArchUnit rule stay — they guard Jackson 2's presence.

Against
Deriving the 45 response types is the larger half and touches three screens. The drift check alone is the cheap first step and already pays.

Follows ARCHITECTURE.md §3 "OpenAPI schema and the Jackson 2/3 split", and completes what the maintenance spec promised: "type drift becomes a CI failure".
